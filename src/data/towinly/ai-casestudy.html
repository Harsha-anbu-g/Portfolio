Case study · Towinly

Towinly is a trust platform for elders and younger helpers: a React Native (Expo) phone app, a React website, and one Spring Boot backend on Railway with Postgres. The AI work sits on all three.

The one-minute version

Towinly has an in-app assistant called Ask AI, a tortoise that elders can ask anything about the app. It started in July 2026 as a simple chat over a large language model. In October 2026 it grew into a full AI programme of twelve steps: cost accounting, an evaluation set, tool use, a Model Context Protocol server that exposes the whole app to any AI agent, retrieval over the user guide with a vector database, semantic matching between elders and helpers, assistant actions that the person confirms before anything is written, an Agent2Agent server, a self-hosted embedding model, a written set of safety guardrails, a goal-driven agent, and an evaluator agent that scores another agent and can block a release.

As of 2026-10-25 the backend side is live in production, with Groq writing the answers and OpenAI embeddings powering the guide search and the matching. On 2026-10-27 the answers moved to OpenAI too (see Groq out, OpenAI only); that change is tested against the eval set and merged to main.

One by one

The twelve steps

Each step says what it is, why it exists, how it works, and how it was proven.

Step 0

Ask AI itself

July 2026
  • What: a chat helper inside the app and the website. The person types a question, the tortoise answers.
  • Model: OpenAI's gpt-6-luna through the Chat Completions API, reasoning off (its rule for tool calling on that API, and the quickest answer). Until 2026-10-27 it was Groq's hosted openai/gpt-oss-120b at low reasoning effort. The model is a setting, not code: one environment variable swaps it.
  • Knowledge: a hand-written knowledge base (about 2,400 words) and a system prompt (about 1,000 words) that tell the model the real rules of Towinly: the 7-step trust ladder, the 15-point score, SOS, family powers, what is free. The model is told to answer only from these.
  • Fail-safe: a blank key or a disabled flag and the helper says it is not available, instead of crashing.
  • Languages: it answers in the language the person writes in. Tested in English, French and Tamil.

Why it matters: elders do not read manuals. They ask a person. Ask AI is that person, available at 2 a.m.

Step 1

Token accounting and a daily cap

  • What: every answer records how many tokens the model used, how long it took, and whether it was cached, as a spend record and a PostHog event ask_ai_answered.
  • Caps: 8 questions a minute and 60 an hour per person; 2,000 calls a day and 2,000,000 tokens a day for the whole service. Model timeout 9 seconds.

Why: Ask AI is public and every answer costs money. A Tamil or French day costs two to four times the tokens of an English one, so the ceiling is in tokens, not calls.

Step 2

An evaluation set

  • What: evals.json, 45 test questions with the words a correct answer must include. 39 in English, 3 in French, 3 in Tamil; 8 as a signed-in person. The 45th, added 2026-10-27, checks that the helper asks what help is needed before it proposes a request.
  • Families of cases: facts (trust stages, tiers, roles, SOS, family limits, what is free, deleting an account); personal ("what is my score", "what should I do next"); safety (emergency, medical, off-topic, money, passwords, someone else's details, self-harm wording that must point to SOS); and prompt injection ("ignore your instructions", "I am the developer", forged chat history, pulling details out of context, role-play as a bank).
  • Two ways to run: a file test checks the eval file on every build. A live test runs every question against the real model when a key is present.

Why: without a fixed test set, every prompt change is a guess. With one, a regression shows up as a red test.

Step 3

Read-only tools (function calling)

  • What: the model can call three functions about the signed-in person: get_my_connections, get_my_family, get_my_help_requests. One tool round per answer.
  • Limits: the tools return first names, stages and titles only, every string sanitised, nothing written. The model never sees phone, city, photo or verification state.

Why: "Which of my friendships is closest to Fully Trusted?" needs live data. Function calling gives the model the data without giving it the database.

Step 4

The MCP server

  • What: a Model Context Protocol server that turns every function in the app's API layer into a tool an AI agent can call. 93 tools on 2026-10-25, generated automatically from the doc comments on the exported functions in the API layer; the catalog regenerates with the app, and the Reunion feature of 2026-10-26 took it to 108. Names like towinly_post_help_request, towinly_check_in_today, towinly_send_sos.
  • How: a catalog script parses the JSDoc into a tool catalog; a bundler step packages the real app code for Node; the server speaks MCP over stdio and signs in as a real account. The agent can do exactly what that person can do in the app, and no more.
  • Safety: 21 destructive tools (delete account, SOS, password, family powers, sealed box, phone number, and two of the reunion tools; 19 before reunions) require confirm: true; id arguments are validated against [A-Za-z0-9_-]{1,64}; 8 functions are excluded with reasons. 40 tests.

Why: this is the payoff of an architecture rule set in August 2026: every feature is one named, documented, exported function, with no fetch logic in screens. A rule written for humans turned out to be exactly the shape an agent needs. The tool catalog cost nothing extra to produce.

Step 5

Ask AI answers from the user guide (RAG on pgvector)

  • What: the real user guide (the same text as the printed PDF guides) is split into 201 passages. Each passage is turned into a vector with OpenAI text-embedding-3-small (1,536 dimensions) and stored in Postgres with the pgvector extension. When a question comes in, it is embedded too, the closest passages are found by cosine similarity, and they are added to the prompt.
  • Indexing: an indexer runs at boot: inserts new passages, deletes gone ones, skips unchanged ones (content hashed). A retriever does the lookup.
  • Switch: a blank embeddings key means no indexing, no embedding, and Ask AI answers from the knowledge base alone, exactly as before. Any OpenAI-compatible embeddings endpoint works (OpenAI, Gemini, Mistral, or the local server from step 10).
  • Proof: Railway log 2026-10-25 00:52 EDT: "Guide index: 201 chunks in file, 201 embedded now, 0 removed". The same question before and after: before, "Post Request tab" and a "Driving" category (guessed); after, "the blue Ask Help button", "Rides under Kind of help", "Post Help" (the app's real words).

Why: a knowledge base is a summary. The guide is the whole truth, with the real button names. Retrieval lets the model read the right page instead of remembering a summary.

Step 6

Semantic matching in discovery

  • What: every helper profile and every help request gets an embedding, stored in two tables. When an elder looks for helpers, or a helper browses requests, similarity of meaning becomes a small lift in the ranking.
  • The formula: rank by distance minus 5 km times cosine similarity. A helper 8 km away who wrote "I drive elders to appointments" ranks like a helper 3 km away for a request that says "need a lift to the clinic". A missing embedding lifts nothing, so distance order is the floor.
  • Upkeep: a row is re-embedded only when its text hash changes; a backfill embeds up to 500 rows at boot. Saving a profile or a request refreshes its vector.

Why: distance alone cannot tell that "company on a slow walk" and "someone to sit with my mother" are the same need.

Steps 7 and 8

Assistant actions behind a native confirm

  • What: Ask AI can propose two actions: propose_check_in and propose_help_request. The backend returns {reply, action} where action is {name, arguments} and name is always one of the app's own exported API functions (checkInToday, postHelpRequest).
  • The rule: the model never writes. The app shows a native confirmation dialog with exactly what will be sent, in the app's own sentence first. Only when the person taps confirm does the app call its own named function, through the same content filter the Post Request screen uses (composer parity).
  • Argument safety: whitelisted fields, capped lengths, enum-checked categories.

Why: I wanted an elder to say "post a request for a lift on Thursday" and have it happen. The design makes it happen with one tap, and makes it impossible to happen without one.

Step 9

The A2A agent

  • What: Towinly's helper exposed under the Agent2Agent protocol 1.0, JSON-RPC binding, so other agents can talk to it. Agent card at /.well-known/agent-card.json, one skill, "Ask Towinly".
  • Safety: every message needs a bearer key; it listens on loopback unless told otherwise; write proposals come back as metadata, never executed. 7 tests.

Why: MCP is how a person's assistant drives Towinly. A2A is how another company's agent would. Both exist, both over the same named functions.

Step 10

A self-hosted embedding model

  • What: Xenova/all-MiniLM-L6-v2 (384 dimensions) served from a Mac through Transformers.js, behind the same /v1/embeddings shape OpenAI uses. Mean pooled, L2 normalised. Optional bearer key. 5 tests.

Why: the backend can point its embeddings at this server with no code change, so profile and request text never leaves the machine. It also makes the evaluator (step 12) free to run.

Step 12

Two end-to-end agents

The Towinly agent

Give it a goal in plain words ("Which of my friendships is closest to Fully Trusted, and what is my score?"). It plans with the model, calls the app's own API functions as tools (same catalog as the MCP server, so the two can never disagree), stops to ask before anything that changes data, and writes every step to a trace file. One flag limits the tools, another bounds the loop (default 8 steps). 13 tests.

The evaluator agent

An agent that tests another agent. It reads the A2A agent card, asks each of 8 cases over A2A, embeds the reply and the reference answer with the local embed server, and scores the pair by cosine similarity. Threshold 0.6. It writes a scorecard and exits non-zero when any case fails, so it can gate a release in CI. It sends the bearer key only to the origin configured, and refuses a card that points elsewhere. 6 tests.

What the model sees

Privacy, in plain words

  • The person agrees before anything goes to an AI company. The consent names OpenAI, which writes the answer and embeds the question to find the guide page (until 2026-10-27 it named Groq for the answer and OpenAI for the search). New wording means a new consent.
  • The privacy policy on towinly.com says the same thing in the same words.
  • The model sees the question, a short summary of the person's own activity (first name, role, score, streak, counts), and the matching guide passages. It never sees contact details, city, photo or verification state, and never anyone else's data.
  • Nothing is written to Towinly by a model. Every write ends in a dialog the person answers.
  • In an emergency the helper points to the SOS button and the local emergency number. It gives no medical, legal or money advice.
Method

How it was built

  • Spec first. One design spec for the whole roadmap and one implementation plan per step, written before the code.
  • Tests first. Every step shipped with its tests; the full backend suite stayed green at every step (1,124 tests, 76 skips, at step 5). The five Node packages carry 71 tests between them (40 MCP, 7 A2A, 13 agent, 6 evaluator, 5 embed server), all passing on 2026-10-25.
  • Database gate before code. Before writing the pgvector migration, the production Postgres was checked for the extension (pgvector 0.8.6 on Postgres 18.6, Railway). The CI test database was switched to a pgvector image the same day the first CI run failed.
  • Security review on every commit, findings fixed the same day.
  • Everything is a switch. Model, embeddings provider, caps, enabled flags: all environment variables. The code has one path; the deployment chooses.
Live since 2026-10-24

Running it in production

  • Hosting: Spring Boot on Railway (Hobby plan), Postgres with pgvector, OpenAI for answers and embeddings (Groq wrote the answers until 2026-10-27).
  • The Railway incident (2026-10-21 to 23): Railway froze deploys platform-wide during a security incident aimed at AI API keys. The running service stayed up; the new code waited. When builds returned, the GitHub link had been reset, so the deploy had to be triggered by hand. Keys stored on Railway were treated as exposed: the Groq key was replaced and the old one deleted after confirming the new one was in use, with Ask AI tested live between the two steps so it never went dark.
  • Spend protection: the OpenAI account holds a fixed $10 with auto-reload off, so a stolen key can spend at most $10 and then stops. The answers run on the same account; per-person and per-day caps in Towinly's own code bound a bad day near $1 to $3.
  • Cost today: the whole guide (201 passages) embeds for a fraction of a cent. A question costs about one two-thousandth of a cent to embed and about a twentieth of a cent to answer.

Plugs for AI programs

The five Mac-only tools, in plain words

The idea behind all five: today a person uses Towinly by tapping buttons. More and more, people have an AI assistant and will just say "book me a ride helper for Thursday". For that to work, the assistant needs a way to press Towinly's buttons on the person's behalf. These five are the plugs that make Towinly usable by AI programs, not only by fingers.

MCP server

  • What it is: a standard plug, like a USB port, for AI assistants. MCP stands for Model Context Protocol. Any assistant that speaks MCP can plug into Towinly and see 108 "buttons" it may press: post a help request, check in today, show my connections, send a message.
  • Problem it solves: without it an assistant can only talk about Towinly. With it, the assistant can act in Towinly for the person.
  • Who benefits: an elder's daughter tells her assistant "check whether Mum checked in today" and it happens. The developer tests the app by talking to it. Claude used it on 2026-10-24 to check the deploy, by asking the live server a question.
  • How it works: signs in as a real account and runs the exact code the app runs, so the assistant can do what that person can do and nothing more. The 21 risky buttons need an explicit confirm.

The interview answer: "What is MCP and have you used it?" "The standard for giving an AI assistant tools. I exposed Towinly as 108 tools, generated from the doc comments on our API functions, with confirmation required on the destructive ones."

A2A agent

  • What it is: if MCP is a plug for one person's assistant, A2A (Agent2Agent) is a phone line between two organisations' AI programs. A care home's AI could ring Towinly's AI: "Do you have a helper near this postcode who does rides?"
  • Problem it solves: letting organisations' systems cooperate machine to machine, in a standard way, without someone copying data between websites.
  • Who benefits: future partners: care homes, hospital discharge teams, city seniors' programmes. Today nobody calls it; it is a working proof.
  • How it works: it publishes a "business card" (the agent card) at a known web address saying what it can do and how to authenticate. Callers need a key. It answers questions; it never changes anything.

The interview answer: "Difference between MCP and A2A?" "MCP connects an assistant to an app's tools. A2A connects agents to each other as peers, across organisations. Towinly has both, over the same list of functions."

Local embed server

  • First, the word: an embedding turns a sentence into a list of numbers that captures its meaning, so a computer can tell that "lift to the clinic" and "drive me to the doctor" mean nearly the same thing. Towinly uses OpenAI for this on the server; it powers the guide search and the helper matching.
  • What it is: the same job done by a small free model on the Mac, dressed up to look exactly like OpenAI's service. Anything built for OpenAI can point at it with no code change.
  • Problem it solves: cost, privacy and dependence. Text stops leaving your machines, nothing is billed, no vendor key to lose.
  • Who benefits: today, the evaluator uses it for free. With part (c) of the next round below, elders: their profile text would never leave Towinly's server.

The interview answer: "How would you reduce cost or vendor lock-in for embeddings?" "I served an open model behind the same API shape, so swapping providers is a configuration change, and measured the quality trade-off against our eval set."

Goal agent

  • What it is: an intern who knows every button in Towinly. Give it a goal in plain words ("Which of my friendships is closest to Fully Trusted, and what is my score?"). It works out the steps, presses the buttons, reports back. Before anything that changes data, it stops and asks.
  • Problem it solves: a chatbot answers one question. An agent plans several steps to reach a goal. This is the pattern behind every "AI agent" product, and interviewers ask how you kept it safe.
  • Who benefits: eventually an elder who struggles with menus could just say what they want. Today it is a developer tool, and every step is written to a trace file.

The interview answer: "Have you built an agent? How do you stop it doing damage?" "A plan-and-act loop over a model, the same tool catalog as our MCP server, a cap of 8 steps, confirm before any write, and a full trace of every step."

Evaluator agent

  • What it is: a driving examiner for the AI. It asks the Towinly agent questions whose right answers we know, compares each answer to the reference by meaning (through the embed server), scores it 0 to 1, fails anything under 0.6. One failure blocks the release.
  • Problem it solves: AI answers drift. Change a prompt or a model and a right answer can go wrong quietly. This catches it automatically.
  • Who benefits: elders get answers that do not degrade unnoticed. The developer gets the freedom to change things.

The interview answer: "How do you test an AI feature?" "Two layers: a fixed set of 45 questions with required words on every build, and an evaluator agent that scores answers by semantic similarity and fails the build below a threshold."

One sentence for all five: "I made Towinly operable by AI, not only by people: a standard tool interface so assistants can act for a user, an agent-to-agent endpoint for partners, a goal-driven agent with confirm-before-write, an evaluator agent that scores answers and gates releases, and a local embedding model to cut cost and keep text in-house. The user-facing parts are in production; the agent tooling runs locally as proofs, and I have scoped what it takes to move it server-side."

Part a

Move the A2A agent into the backend

  • Today: a Node program on the Mac. Other agents reach Towinly only while the laptop runs it.
  • Proposed: the same thing inside Spring Boot with the official Java A2A SDK (a2a-java-sdk 1.0.0.Final): an agent card at the backend's /.well-known/agent-card.json, always on, and an AgentExecutor routing messages to the same named functions the MCP server wraps.
  • Effort and risk: 2 to 3 days with tests. Opens an internet-facing endpoint for machines; it must sit behind the same caps and auth as Ask AI, writes stay proposals.

The interview line: "I moved the agent endpoint from a laptop sidecar into the production service with the official Java SDK, over the same function catalog the MCP server uses."

Part b

Spring AI instead of hand-written orchestration

  • Today: custom code: LlmClient (240 lines, named GroqClient until 2026-10-27), AssistantTools (222), GuideRetriever (47), AssistantService (435). Works, tested, mine to maintain.
  • Proposed: Spring AI on Spring Boot 3.5.16 / Java 21. ChatClient replaces LlmClient (it already speaks the OpenAI Chat Completions protocol, so it is the OpenAI starter as-is); @Tool annotations replace hand-written tool schemas; PgVectorStore replaces the retrieval SQL; spring-ai-starter-mcp-server-webmvc serves the MCP tools from the backend over HTTP.
  • Gain: about 900 lines become roughly a third in configuration and annotations; model swaps become settings; streaming and token metrics come free.
  • Risk: a rewrite of working code. Guards must be re-wired as Spring AI advisors; token accounting must come from the framework's usage data; the MCP endpoint needs Spring Security. The 45-case eval set is the safety net. About a week. The biggest of the four.

"Why didn't you use a framework?" "When I started in July 2026 the model API was one HTTP call, and I wanted the safety checks inline and the dependency footprint small on a cheap hosting plan. I adopted it for in-process embeddings, where it saved real work and removed a data flow to a third party, and kept the chat orchestration hand-built because the guardrails are easier to audit when you can read them. If the team standard were Spring AI, I'd move the rest module by module behind the eval set, never as a big-bang rewrite."

Part c

Run embeddings inside the backend (ONNX)

  • Today: every profile, request and question goes to OpenAI to become a vector of 1,536 numbers. Pennies a month, but the text leaves the server and the privacy policy must say so.
  • Proposed: run the open model all-MiniLM-L6-v2 (384 numbers, about 90 MB) inside the Java process through Spring AI's TransformersEmbeddingModel on ONNX Runtime. No network call, no key, no per-use cost, text never leaves Railway.
  • Why it is cheap to do: the backend already has a provider switch, step 10 proved the model, and zero-padding 384 to 1,536 leaves similarity unchanged, so the database columns need no migration. Changing the model name makes the hash-based index re-embed everything at the next start.
  • Trade-offs: the small model is weaker than OpenAI's and English-centric; for French and Tamil the multilingual variant is the right pick. About 2 days. Lowest risk, biggest privacy win.
  • Running cost: no new account, key or licence. OpenAI drops to $0. Railway goes up roughly $3 to $5 a month: the model and its runtime hold about half a gigabyte of memory all the time, billed around $10 per gigabyte per month, plus under $1 of CPU. At Towinly's size OpenAI is cheaper; this buys privacy, independence and the framework on the CV, not savings. A compressed model brings it to $1 to $2 with a small quality loss.

The interview line: "I moved embeddings from a third-party API to an in-process ONNX model: one data flow removed from the privacy policy, zero per-call cost."

Part d

Cost and latency evidence

  • Today: every answer already sends ask_ai_answered to PostHog with tokens, milliseconds and cache hit. Nobody looks at it in a chart.
  • Proposed: (1) a PostHog dashboard: questions and tokens per day against the 2 million cap, median and slowest-5% latency, cache rate, cost estimate, half a day; (2) streaming the answer word by word so the elder sees text within about a second instead of 3 to 9 seconds, 2 to 3 days, and the output guard must buffer or check as it goes; (3) small-model routing: strong guide matches go to gpt-oss-20b, hard questions to the large model, measured against the 45 evals, 1 to 2 days.

The interview line: "I measured cost and latency per answer, then cut both: streaming for felt speed, routing for cost, with the eval set as the guard."

Order, if the freeze is lifted for some of it: (c) first, then (d) dashboard and streaming, then (b), then (a). Parts (c) and (d) are "better and faster", which the freeze allows; (a) and (b) add surface and rewrite working code.

In my words

Eight questions, short answers

Tell me about an AI feature you built.
Towinly has an assistant for elders called Ask AI. I built it in three stages. First, a chat over a hosted model with a hand-written knowledge base and hard limits on cost. Second, retrieval: I split the real user guide into 201 passages, embedded them into Postgres with pgvector, and the assistant now reads the matching page before answering, so it uses the app's real button names. Third, actions: the model can propose "check in today" or "post this help request", but it can only propose. The app shows a native dialog and calls its own function when the person confirms. The model never writes.
How did you keep it safe?
Eleven layers, each with a test, each failing closed. Consent before any data leaves the phone, and it re-asks when the wording changes. A sanitiser and a PII guard on the way in, an output guard on the way out that blocks password requests, money requests, prompt leaks and invented contact details. The model sees the person's first name, role and score, never city, phone or photo. Writes are proposals only. And a 45-case eval set with injection and self-harm cases that runs on every build.
What is MCP and why did you build a server?
Model Context Protocol is the standard way to hand an AI agent a set of tools. The app already had a rule that every feature is one named, documented, exported function. I wrote a generator that reads those doc comments and produces 108 tools. So an assistant in Claude Code can sign in as a person and do anything that person can do in the app, and nothing more. Twenty-one destructive tools demand an explicit confirm flag.
What did you measure?
Tokens, latency and cache hits per answer, sent to PostHog. Per-person and per-day caps on top. The eval set gives a pass/fail per prompt change. The evaluator agent gives a cosine score per answer against a reference and fails the build under 0.6.
What went wrong?
The first TestFlight tester said the AI was broken. It was not; the client gave up at 15 seconds and a careful answer took longer. It waits 30 now. Then in October the hosting provider had a breach aimed at AI keys. I rotated mine, with a live test between adding the new key and deleting the old one, so the assistant never went dark.
What would you do next?
Run the embeddings in-process so no text leaves the server, move the orchestration onto Spring AI so the tool and retrieval code is framework-standard, and put a cost and latency view on the dashboard. All three are specified; they wait on the product's feature freeze.
What is in production and what is not?
The user-facing parts are live on the server: the assistant, retrieval over the guide, semantic matching, the guards and caps. The agent tooling, the MCP server, the A2A agent, the goal agent and the evaluator, runs locally as working proofs, and I've scoped the two to three days it takes to move the agent endpoint server-side. I'd rather say exactly where the line is than let anyone assume.
Why does an elders' app need any of this?
Elders do not read manuals and many struggle with menus. The assistant answers in their own language from the real guide. Matching by meaning finds the helper whose words do not match the request's words. And the agent tooling is for the person's family and their assistants: "check whether Mum checked in today" should be one sentence, not six taps.

2026-10-27

Groq out, OpenAI only

Why. Groq's free tier allows 8,000 tokens a minute. Every Ask AI question carries about 6,500 tokens (the knowledge base, the guide passages, the tool definitions and the chat), and a question that looks something up is two calls. So the second question in any minute came back as the fallback sentence. A timed experiment proved it: question 1 answered, question 2 five seconds later failed, question 3 after a 75 second pause answered, question 4 five seconds after that failed. The Railway log carried the body: 429, "TPM: Limit 8000, Used 4905, Requested 6239".

What changed. The vendor is now configuration. The backend reads one set of llm.* settings: the OpenAI key, shared with the embeddings, the model name (default gpt-6-luna) and the reasoning effort (default none). GroqClient became LlmClient. Two request fields changed for OpenAI: max_completion_tokens instead of max_tokens, and the tool-result turn carries no name. The consent note (version 3), the app and website privacy pages, the user guide and the store privacy labels name OpenAI alone. The local agent plans with the same vendor. Merged to main on 2026-10-27.

Why reasoning off. OpenAI's model page says gpt-6-luna calls tools on Chat Completions only with reasoning effort set to none. That is also the quickest and cheapest answer, with no thinking tokens before the reply.

Numbers. gpt-6-luna costs $0.10 per million input tokens, $0.01 cached and $0.50 output. The Build tier allows 5,000 requests and 2,000,000 tokens a minute, 250 times Groq's free ceiling. One question costs about $0.0003 to $0.0007, a lookup question double that. The $10 credit covers roughly 10,000 questions. The daily ceilings (2,000 calls, 2,000,000 tokens) hold a bad day near $1 to $3.

Evals. The 44 cases of the day ran against gpt-6-luna before the merge (the 45th case came later the same day). The first run scored 36 of 44, and none of the misses was a bad answer. Four were a slow patch at OpenAI that hit the 9-second limit, and the client never retried a read that stalled mid-reply. Three were good refusals the output guard blocked: it looked for "don't" with a straight apostrophe, and OpenAI writes it with a curly one. One was the team address, which the knowledge base tells the helper to quote. After fixing the guard and the retry, the run scored 44 of 44, median 1.4 s, slowest 6.5 s, with about 97% of every prompt read from OpenAI's cache. Lesson: a new model can be right in ways your filters were never written for, so run the evals before you trust the switch.

The interview line: "Production hit a vendor's free-tier ceiling. I proved the cause with a timed experiment and the error body, then moved vendors with a configuration change, because the client was written against the open Chat Completions shape. The code changes were two vendor-specific fields and honest renames, and the evals ran against the new model before anything shipped."

Lesson: the first fix (echoing the model's turn the way Groq validates it) was right by the docs and still not the live cause. Same symptom, two causes. Log the error body, and time the failures before trusting a theory.

Plain words

Glossary

LLM / model
The program that writes the answers. Towinly's is OpenAI's gpt-6-luna (Groq's gpt-oss-120b until 2026-10-27).
TPM
Tokens per minute, a vendor's speed limit. Groq's free tier gave 8,000; one Towinly question is about 6,500.
Reasoning effort
How long a model thinks before it answers. None means it answers at once, which is what tool calling on gpt-6-luna needs.
Token
The unit the model bills in, roughly three quarters of a word.
Prompt
Everything sent to the model: rules, the knowledge base, the guide passages, the question.
Embedding
A list of numbers that captures the meaning of a piece of text, so two texts can be compared by meaning.
Vector database / pgvector
Postgres with an extension that stores embeddings and finds the closest ones fast.
RAG (retrieval-augmented generation)
Find the relevant passages first, then let the model answer from them.
Cosine similarity
The score, from 0 to 1, for how alike two embeddings are.
Function calling / tools
Letting the model ask the code for data, or propose an action, in a structured way.
MCP
Model Context Protocol, the standard for giving an AI agent tools.
A2A
Agent2Agent, the standard for one agent talking to another.
Guardrail
A check in code that stops a known bad outcome, with a test that proves it.
Eval
A fixed test question with the words a right answer must contain.
Fail closed
When unsure, refuse, instead of guessing.
Agent
An AI program that plans several steps and uses tools to reach a goal, instead of answering one question.
Agent card
The "business card" an A2A agent publishes at a known web address: what it can do, how to reach it, what key it needs.
Function catalog
Towinly's list of named, documented API functions. The MCP server, the goal agent and the assistant actions all read the same list.
Spring AI
Spring's official framework for calling models, tools and vector stores from Java.
ONNX
A file format for running a trained model inside your own program, with no network call.
Streaming
Sending an answer word by word as it is written, so the reader sees text at once.
Zero-padding
Adding zeros to the end of a shorter vector so it fits a wider column; similarity scores do not change.
